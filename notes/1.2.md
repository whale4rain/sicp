# 1.2 Procedures and the Processes They Generate

> Lab: [SICP 1.2 Lab](../labs/sicp-1-2-lab.html) (1.2.1–1.2.3) · Previous: [1.1](1.1.md) · Next: [1.3](1.3.md)

**Big idea:** a **procedure** is the text you write; a **process** is what happens when it runs. To be good at programming you have to predict the process from the procedure: its *shape*, and how much time and space it uses as the input grows.

## 1.2.1 Linear recursion and iteration
```scheme
;; recursive process
(define (factorial n)
  (if (= n 1) 1 (* n (factorial (- n 1)))))

;; iterative process
(define (factorial n) (fact-iter 1 1 n))
(define (fact-iter product counter max-count)
  (if (> counter max-count)
      product
      (fact-iter (* counter product) (+ counter 1) max-count)))
```
```scheme
; recursive process                ; iterative process
(factorial 4)                      ; (fact-iter 1 1 4)
(* 4 (factorial 3))                ; (fact-iter 1 2 4)
(* 4 (* 3 (factorial 2)))          ; (fact-iter 2 3 4)
(* 4 (* 3 (* 2 (factorial 1))))    ; (fact-iter 6 4 4)
(* 4 (* 3 (* 2 1)))                ; (fact-iter 24 5 4)
(* 4 (* 3 2))                      ; 24
(* 4 6)
24
```
- **Recursive process**: builds a chain of **deferred operations**, then performs them while contracting. The interpreter must remember the chain, so space grows with n. Shape: expands then shrinks.
- **Iterative process**: its whole state fits in a fixed set of **state variables**, plus a rule for updating them and a stopping test. Stop it at any step, write down `product counter max-count`, and you can resume. Constant space.
- A **recursive procedure** (it refers to itself) can generate either kind of process. Don't confuse the two words.
- Scheme is **tail-recursive**: a call that is the last thing a procedure does uses no extra space. So iteration needs no `for`/`while`; those are just syntactic sugar elsewhere.
- Quick test: is anything left to do *after* the recursive call returns? If yes (`(* n (factorial ...))`), recursive process. If the call *is* the result, iterative.

## 1.2.2 Tree recursion
```scheme
(define (fib n)
  (cond ((= n 0) 0)
        ((= n 1) 1)
        (else (+ (fib (- n 1)) (fib (- n 2))))))
```
- Each call branches into two, so the process is a tree. `(fib 5)` computes `(fib 3)` twice and `(fib 2)` three times.
- Steps grow like Fib(n) itself, which is ≈ φⁿ/√5 with φ = (1+√5)/2 ≈ 1.618 (exercise 1.13): **exponential**. Space is the depth of the tree: **linear**.
- Iterative version: slide two state variables along the sequence, `a ← a + b`, `b ← a`. Linear steps, constant space.
```scheme
(define (fib n) (fib-iter 1 0 n))
(define (fib-iter a b count)
  (if (= count 0) b (fib-iter (+ a b) a (- count 1))))
```
- Tree recursion isn't useless: it's the natural way to express problems on hierarchical data, and often far easier to write. **Counting change** (how many ways to make change for an amount with 5 kinds of coins) is easy as a tree recursion and hard to make iterative:
  - ways(amount, coins) = ways(amount, all but the first coin) + ways(amount − first coin, coins)
  - base cases: amount = 0 → 1 way; amount < 0 or no coins → 0 ways.
- A smarter compiler, or **memoization** (tabulation, exercise 3.27), can turn redundant tree recursion into something efficient.

## 1.2.3 Orders of growth
- R(n) is **Θ(f(n))** if there are positive constants k₁, k₂ with k₁f(n) ≤ R(n) ≤ k₂f(n) for large n. It ignores constant factors and describes how the resource *scales*.

| Process | Steps | Space |
|---|---|---|
| recursive factorial | Θ(n) | Θ(n) |
| iterative factorial | Θ(n) | Θ(1) |
| tree-recursive fib | Θ(φⁿ) | Θ(n) |
| iterative fib | Θ(n) | Θ(1) |
| count-change (k coin kinds) | Θ(nᵏ) | Θ(n) |
- A process that **halves** the problem each step takes Θ(log n). Doubling n then costs only one more step.
- Orders of growth are crude, but they tell you what happens when the problem gets bigger, which is usually the question that matters.

## 1.2.4 Exponentiation (week 3)
```scheme
(define (fast-expt b n)
  (cond ((= n 0) 1)
        ((even? n) (square (fast-expt b (/ n 2))))
        (else (* b (fast-expt b (- n 1))))))
```
- bⁿ = (b^(n/2))² when n is even, b·bⁿ⁻¹ when odd. Θ(log n) steps instead of Θ(n).
- Exercise 1.16 makes it iterative using an **invariant quantity**: keep a·bⁿ unchanged from step to step, with a starting at 1 and ending as the answer. Invariants are the general tool for designing iterative algorithms.

## 1.2.5 Greatest common divisors (week 3)
```scheme
(define (gcd a b)
  (if (= b 0) a (gcd b (remainder a b))))
```
- **Euclid's algorithm**: GCD(a, b) = GCD(b, a mod b). An iterative process.
- **Lamé's theorem**: if Euclid takes k steps, the smaller input is at least Fib(k). So steps are Θ(log n).
- Exercise 1.20 replays it under normal-order evaluation to count how many `remainder` calls happen (a lot more).

## 1.2.6 Testing for primality (week 3)
- **Search for divisors** from 2 up to √n: Θ(√n) steps.
- **Fermat's little theorem**: if n is prime and a < n, then aⁿ ≡ a (mod n). Pick random a and check; if it fails, n is definitely composite. If it passes many times, n is *probably* prime. Θ(log n) per test using `expmod`:
```scheme
(define (expmod base exp m)
  (cond ((= exp 0) 1)
        ((even? exp) (remainder (square (expmod base (/ exp 2) m)) m))
        (else (remainder (* base (expmod base (- exp 1) m)) m))))
```
- Taking `remainder` at every step keeps the numbers small; that's why it beats computing aⁿ first (exercise 1.25).
- **Probabilistic algorithms**: the answer is only probably right, but the chance of error can be made smaller than the chance of a hardware fault.
- **Carmichael numbers** (561, 1105, 1729, …) fool the Fermat test for every a (exercise 1.27). The **Miller–Rabin test** (exercise 1.28) can't be fooled this way.
